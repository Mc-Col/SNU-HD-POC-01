진한 파란 박스가 AI 호출 지점이다. 분기는 모두 내용 기반이며 확장자로 판단하는 곳은 없다.

Ground Truth

실물이 바꾼 규칙 네 개

아래는 모두 문서를 열어보고 정해진 것이다. 추정으로 세운 규칙은 두 번째 파일에서 깨졌다.

① 페이지 선택 — 태그가 아니라 최신성

한 파일에 사양표가 여러 장이면 가장 최신인 한 장만 본다. 처음에는 "파일명 태그가 단독으로 나오는 페이지"를 골랐고, 그것은 틀렸다.

10FV011-DATA SHEET_REV1.tifp1p4
발행2003 Valstone Retrofit1986 Nippon Fisher
태그011 / 012 / 013 / 014011 단독
표기WORK SCOPE — 신규교환수기 "OLD"
MODEL NO.667-ED657-ED
RATED CV9570.7
태그 단독성으로 고르면 MVP 두 필드가 틀린다

같은 파일의 준공검사보고서(CVT-030526-1)가 p1 의 값을 독립 확증했다. 태그 대조는 선택 기준이 아니라 선택 후 검증으로 강등했다. 그리고 결정론적인 오답은 매번 같은 답을 내므로 더 발견하기 어렵다 — 흔들리는 값은 의심을 사지만 일관된 값은 검증을 통과한다.

그런데 사양표가 두 장이라고 다 같은 문제가 아니다. 판별자는 태그 교집합이다.

상황태그 교집합판정
10FV011 — p1[011,012,013,014] · p4[011]있음 같은 설비의 다른 시점 → 최신을 고른다
070100 견적서 — p4[B10TV040] · p5[B10TV1016]없음 서로 다른 설비 2대 → 파일명 태그로. 없으면 "자산 N건 발견"

② 태그 — Area 는 문자+숫자, 없으면 A 가 생략된 것

Area - 설비종류 - 일련번호. 1공장이 최초 공장이라 지을 때 구분이 필요 없었고, 2공장부터 B 를 붙였다. 즉 10-FV-012 의 정식 표기는 A10-FV-012 다.

버린 한 글자가 서로 다른 설비를 합친다

정규화에서 앞 문자를 버리면 10-FV-012(A10 구역)와 B10-FV-012(B10 구역)가 같은 값이 된다. 현재 코퍼스 충돌은 0건이라 테스트도 통계도 정상으로 보였다. 증상은 30만 태그에서만 나타나고, 그때는 두 설비의 이력이 이미 섞여 있다 — 기준정보 오염을 막는 시스템이 오염시키는 코드를 품고 있었다.

용도값쓰는 곳
정규화 키A10FV011파일명↔문서 대조, 페이지 검증
내보내는 값10FV011화면·엑셀 — 문서에 없는 A 를 만들지 않는다
표시implicit_plant=True규칙으로 채웠다는 기록

③ 범위 — 정비보고서는 대상이다

한때 112건을 제외했다. 근거는 정엔지니어링 발행 체크시트의 사양 칸이 대부분 비어 있다는 실측이었다 (22칸 중 2~12칸). 그 판단을 철회했다.

비어 있는 것은 수율 문제이고 범위 문제가 아니다

스캔해서 비면 시스템이 N/A + 사유로 정직하게 답하는 것이 옳은 동작이고, 그 동작 자체가 이 과제의 산출물이다. 제외하면 아예 보지 않게 되고 데이터시트가 없는 34개 태그는 영구 도달 불가가 된다. 실물 반례도 있다 — Valstone 발행 10PV018-REPAIR REPORT 는 시트 3 에 CONTROL VALVE SPECIFICATIONS 가 텍스트로 온전히 있다.

단 억지로 채우지 않는다. 읽히는 것만 적고 나머지는 N/A + 사유다. "이 문서로는 채울 수 없다" 가 측정 대상이다.

판정건수비율
대상1,02196.4%
제외 — 도면 · 계기목록131.2%
판단 불가 → 내용 판정으로252.4%

대상 1,021건의 포맷 — tif 71.9% · pdf 16.6% · xlsx·xlsm 11.6%. 그중 정비·개조 보고서 112건(11.0%)이고 111건이 텍스트 레이어를 갖고 있다.

④ VLM 과 텍스트 레이어의 역할

VLM 이 어느 텍스트가 어느 필드인지 정하고, 텍스트 레이어가 그 글자를 보증한다

텍스트 레이어가 온전한 PDF 에서도 뽑아보면 OPEN/CLOSE 가 한 덩어리로, 색상값이 라벨과 멀찍이 떨어져 나온다. 글자는 100% 있는데 어느 값이 어느 필드인지 알 수 없다. 표 구조가 무너진 텍스트는 값의 목록일 뿐이다.

비용 절감은 페이지 수를 줄이는 데서 얻고, 판독 단계를 생략해서 얻지 않는다. 8페이지를 격자 한 장으로 판정해 VLM 호출을 8회 → 2~4회로 줄인다.

Cost

비용 사다리에 모델 축을 더한다

원래 사다리는 규칙 검증(무료) → 평가 Agent(유료) → HITL(가장 비싸다) 였다. 여기에 모델 단계를 하나 더 붙인다.

1차 · 전량gpt-5.6-luna 모든 필드를 싼 모델로 먼저 읽는다
재시도 · 실패분만 gpt-5.6-terra Loop A 가 필드 단위로 돌므로 상위 모델은 실패한 필드만 본다. 28필드 중 3개 실패면 3개분
Rule 과 Note 는 모델에 가지 않는다

"매 루프마다 규칙을 읽으면 컨텍스트 비용이 크지 않나" — 구조를 확인한 결과 그렇지 않다. guidance.yaml 은 사람이 보는 화면만 읽고, domain_rules· value_aliases·unit_tokens·composite_labels 는 파이썬에서 추출 이후에 적용된다.

모델에 가는 것은 필드 정의(name·desc·aliases) 뿐이고 문서당 1회다. 그래서 "1차는 규칙 없이"는 오히려 비싸진다 — aliases 가 없으면 Valve Coefficient → rated_cv 매핑이 안 되어 벤더 변종 대부분이 상위 모델로 올라간다. 반복되는 정적 프롬프트는 빼는 것이 아니라 prompt caching 으로 해결한다.

Measure

무엇을 맞다고 볼 것인가

평가 규칙은 모든 측정의 분모다. 여기가 틀리면 이후 숫자가 전부 틀린다.

원칙같다고 본다다르다고 본다
단위 표기142.6 m3/Hr = 142.6 M3/H = 142.6 m?h 142.6 ≠ 142.5
로마자CLASS 4 = CLASS IV CLASS 4 ≠ CLASS 2
재질 등급—A351 CF8M ≠ A351 CF3M 숫자로 뭉개지 않는다
N/ANA = 빈칸NA ≠ 0 · NA ≠ 판독불가
표기 변종—EQ% ≠ Equal Percent — 별칭 사전의 몫
레귤레이터는 따로 집계한다 — 빼지는 않는다

자기구동 감압변은 액추에이터가 없어 필드가 구조적으로 존재하지 않는다. 실측(Fisher 627) — 28필드 중 12개가 N/A 이고 MVP 9필드 중 2개(RATED CV, 안전 필드 FAIL ACTION)가 N/A 다.

범위에서 빼지 않는 이유는 판별자가 태그가 아니기 때문이다 — PCV 중 레귤레이터는 53% 이고 나머지 절반은 실제 컨트롤밸브다. 그리고 레귤레이터는 이 과제의 핵심 주장(모르면 만들지 않는다)을 증명할 최고의 표본이다. 빼면 증명할 근거를 버린다. 대신 결과 표를 control_valve / regulator 로 나누고 안전 필드 정확도는 컨트롤밸브만으로 낸다.

100% 정확도는 증명할 수 없다

100건에서 오류 0건이면 95% 신뢰상한이 약 3% 다(rule of three). 발표에서 이 점을 먼저 말한다 — 측정의 한계를 숨기면 숫자 전체가 의심받는다.

Loop

루프가 세 겹이다

"하네스와 루프"는 단일 반복문이 아니라 주기가 다른 루프 세 개다. 각 루프가 고치는 대상이 다르다.

Loop A · 초필드 재시도한 필드의 추출이 실패했을 때 그 필드만 다시 읽는다. 최대 2회. 값을 고친다
Loop B · 분문서 배치문서를 순차 처리하며 필드 단위 로그를 남긴다. 처리량·지연·실패율을 만든다
Loop C · 일규칙 개선로그와 사람의 수정 이력을 분석해 규칙표와 프롬프트를 고친다. 시스템을 고친다

Loop A — 재시도와 판정 분기

설계의 핵심. 재시도는 추출 실패에만 적용되고 제약 위반에는 적용되지 않는다.

제약 위반에 재시도를 걸면 환각을 제조한다

"값이 제약을 위반했다, 다시 확인하라"는 프롬프트는 실질적으로 다른 답을 내놓으라는 지시다. 문서에 진짜로 그 값이 있으면 모델은 제약을 만족하는 값을 만들어 순응하고, 검증을 통과해 자동확정된다. 기준정보 시스템에서 최악의 실패 모드다. 제약 위반은 사람에게 넘긴다.

Loop C — 이것이 스크립트를 하네스로 만든다

평가 하네스 스위치 두 개

--no-vlm — VLM 을 제외한 규칙 단독 구성으로 실행한다. VLM 결합이 실제로 필요했는지를 분리 측정하는 유일한 방법이며, 없으면 방법론 선정이 사후 정당화로 남는다.

--holdout — 홀드아웃은 1회 개봉 후 잠긴다. 결과를 보고 튜닝하면 측정이 무효가 된다.

Contracts

계약 세 개가 병렬 작업의 전부다

모듈 사이를 넘는 데이터는 이 세 형태만 존재한다. src/contracts.py 에 구현되어 있고 이종수 책임만 수정한다.

계약생산 → 소비핵심 필드
TriageResult① → ② document_class · targets[] · confidence · reason · stats
RawExtraction③ → ④ field_key · raw_value · raw_label · bbox · confidence · parser · source_locator
FieldRecord⑥ → ⑦ · 로그 · 평가 value · state · note · transform_trace · bbox · safety · retry_count · human_action
계약이 규칙을 강제한다 — 문서가 아니라 코드로

FieldRecord.validate() 가 두 가지를 차단한다. 자동확정 외 상태에 비고가 없으면 예외를 던지고, 안전·식별 필드가 자동확정되면 "사람 확인 필요" 표시를 자동 부여한다. 문서로만 적어두면 지켜지지 않으므로 계약 레벨에 넣었다.

raw_label 이 사전을 자동으로 키운다

문서에 실제로 적혀 있던 항목명을 그대로 담는 필드다 — "FAIL POSITION", "INLET PRESSURE MAX". 28필드의 표기 변종을 사람이 상상해서 채우는 것은 불가능하고 실물에서 수집되어야 한다. 파이프라인이 돌면서 유사표현 사전이 자란다.

Hooks

프레임워크가 강제하는 호출

각 Hook 에 KPI 나 안전 속성이 하나씩 걸려 있다. 개발자가 자기 모듈에만 집중할 수 있는 이유이자, 잊으면 측정이 불가능해지는 지점.

Hook시점강제 이유
on_config_load실행 시작스키마·규칙표 버전과 해시 기록 → 재현성
on_stage_enter / exit단계 진입·종료단계별 소요시간 → 운영성과 KPI
on_route_decided파서 선택 후경로별 정확도 분해. 스캔 경로가 유의하게 나쁜지 판단
on_field_extracted원시값 추출 직후raw_label·bbox·확신도 기록. 유사표현 사전의 원천
on_unmapped_label매핑 실패 시사전에 없는 표기 수집 → Loop C 의 입력
on_transform규칙 변환 시transform_trace 생성. 원문 병기의 원천
on_retry재시도 시1·2차 값 비교 → 근거 없는 값 변경 = 환각 탐지
on_violation검증 실패 시위반 유형 기록. 규칙이 과민한지 실제 오류인지 사후 분류
on_state_resolved상태 확정 시자동확정률 집계. 비고 없으면 예외를 던진다
on_escalateHITL 이관 시사유 필수. 없으면 검토자가 판단할 근거가 없다
on_human_action승인·수정 시사람의 판단 기록. 후속 Bandit 학습 데이터
