Reading

매트릭스가 말하는 것 — 셋

우리는 앞칸이 가장 두껍다

S3(범위 좁히기)에서 최신성으로 페이지를 고르는 파이프라인은 우리뿐이다. R3는 내용 유사도(BM25+임베딩)로 고르고, R1·R4·R7은 이 칸이 아예 없다.

그리고 R3의 제거 실험에서 이 칸이 가장 큰 레버였다 — 빼면 15.75~24.02%p 하락으로 다섯 구성 전부에서 1위. 우리가 이미 잘하고 있는 곳이다.

S2가 tif에서 비어 있다

나머지 넷은 이 칸이 전부 채워져 있다 — Textract, PaddleOCR, PDF 바이너리, 계약서 텍스트. 텍스트로 글자를 보증하는 장치가 다들 있다.

우리는 PDF 텍스트 레이어뿐이고, 코퍼스의 71.9%인 tif 734건에는 그마저 없다. 이것이 우리 파이프라인의 가장 큰 구조적 공백이다.

S6이 가장 얇다

R1은 이 칸에 40개 특징을 넣는다. R2는 이 칸 하나만 다루는 논문이다. R7은 이 칸을 위해 LLM을 한 번 더 부른다.

우리는 모델이 스스로 적은 숫자 하나다. 그리고 R2 비교에서 그 방법은 여덟 중 일곱째였다.

R1은 이 40특징을 CatBoost로 결합했고 학습에 필드 단위 1,072표본을 썼다. 우리 골든셋은 30문서 × 28필드 = 최대 840이고 홀드아웃·N/A를 빼면 더 적다. 그래서 같은 결합 방식은 옮기지 않는다 — 특징 3~5개를 로지스틱 회귀로 묶는 데서 시작한다.

M1

가장 확실한 한 가지 — 우리는 이미 두 번 부르고 있다

ExtractConf가 신뢰도를 얻는 방식의 핵심은 성격이 다른 두 호출을 만들고 서로 대보는 것이다. 그 구조가 우리 코드에 이미 있는데, 우리는 둘을 대보지 않는다.

M1두 호출의 교차 일치를 신뢰도 신호로R1 ExtractConf

ExtractConf 는 GPT-4o 를 두 번 부른다. 저자가 두 호출의 성격을 이렇게 갈라 놓았다.

Hunter 는 완성 압박(completion pressure) 아래 있어서, 그 필드가 문서에 분명히 있든 없든 답을 만들어낸다 — 없거나 애매한 필드에 그럴듯한 값을 지어내기 쉽다. arXiv:2606.24420 · Hunter (필드 주도) 정의
Mapper 는 시각적으로 근거가 있는 것만 보고한다(reports only what is visually grounded). arXiv:2606.24420 · Mapper (문서 주도) 정의

둘의 실패 방식이 반대라서 불일치가 곧 위험 신호가 된다. 우리 코드에도 같은 대비가 이미 있다.

우리 Mapper

우리 Hunter

바꾸는 것
MVP 9필드는 실패 여부와 무관하게 reread 를 부르고, 두 값을 문자열 유사도로 비교해 신호로 남긴다.
비용
문서당 9회 추가. 입력은 페이지가 아니라 크롭이라 토큰이 작고, tier1 모델로 돈다. 골든셋 30건이면 270회.

정직하게 적어 둘 것 — 논문에 이 신호(G3) 단독 AUC 수치는 없다. M4(OCR 신호만) 0.896 은 다른 신호군의 값이다. 그래서 채택 전에 골든셋에서 직접 재야 한다. 재는 법은 실험 E2: 일치한 집단과 불일치한 집단의 실제 정답률을 비교해, 불일치 집단이 뚜렷이 낮으면 신호로 성립한다.

M2평가 Agent 를 채점자로 — 추출과 채점을 분리R7 + R2

두 논문이 같은 곳을 가리킨다. R7 은 채점 LLM 을 붙였을 때의 이득을 재고, R2 는 여덟 가지 신뢰도 방법을 같은 조건에서 줄 세웠다.

우리 위치
⑤ Validate 의 평가 Agent 칸. 비용 사다리에 이미 자리가 있다 — 규칙 검증(무료) → 평가 Agent(유료) → HITL.
주의 — 우리 규칙과의 긴장
논문의 채점자는 점수와 함께 수정된 값도 낸다. 우리는 "재시도 프롬프트에 값이 틀렸다고 쓰지 않는다"가 규칙이다.
안전한 이식
점수만 받고 수정값은 받지 않는다. 금지된 것은 "네 답이 틀렸으니 다시 답하라"는 되묻기이고, 채점자는 문서를 직접 보고 독립 판정한다 — 성격이 다르지만 안전한 쪽을 고른다.
비용
필드당이 아니라 문서당 1회로 묶는다. 28필드 값을 한 번에 채점받는다.

운용 지표는 이렇게 읽는다 — 커버리지 80% 에서 자동화 정확도 99.1%. 선별 없이 전부 자동 확정하면 73.3% 다. "자동으로 넘길 비율을 80% 로 잡으면 그중 99.1% 가 맞다"는 문장이 임계를 대신한다.

우리 실험은 E1 → E4 다. E1 은 골든셋 전량을 1회 추출해 자기보고 confidence 와 정오를 함께 기록하고 AUC 와 값 분포를 본다. AUC 가 0.70 을 밑돌거나 값이 0.9 / 0.95 / 1.0 에 뭉치면 단독 사용을 폐기한다. E4 는 신호 3~5개를 로지스틱 회귀로 묶어 곡선을 그린다. 홀드아웃 주의 — 결합 가중치를 학습한 데이터로 임계를 정하면 그 숫자는 부풀려진다. 학습용·보정용·평가용 배분이 먼저다.

M4크롭 선명도를 신호로 — 문서가 원인인 실패를 잡는다R1 G4

ExtractConf 가 로그확률보다 OCR·공간 신호를 높게 친 이유가 여기 있다.

추출 오류는 문서가 원인이지 모델이 원인이 아니다. OCR 신뢰도는 실패 원인을 직접 측정하고, 로그확률은 그것과 무관한 결과를 측정한다. arXiv:2606.24420

프론티어 LLM 은 읽을 수 없는 원본을 읽으면서도 높은 확신을 보인다. 그래서 "이 영역이 실제로 읽을 만한 상태인가"를 이미지에서 직접 재는 것이 값싸고 강한 신호가 된다. G4 의 정규화 라플라시안 점수가 그것이다.

M6실패를 유형으로 나누고 재시도 사다리를 만든다R4 olmOCR

olmOCR 의 최빈 실패는 같은 토큰·줄·문단의 무한 반복이다. 검출은 두 갈래로 한다 — 최대 컨텍스트 초과, 또는 JSON 스키마 검증 실패. 잡히면 temperature 를 0.1 에서 0.8 로 올리고 앵커를 다시 샘플링해 재시도하며, 끝내 실패하면 평문 추출로 폴백한다.

우리 현재
_ask() 가 JSON 파싱 실패 시 예외를 올린다. 삼키지 않는다는 점에서 같은 방어다 (철학 5).
구분되지 않는 것
길이 초과로 잘린 JSON 과 형식이 깨진 JSON 이 같은 예외로 뭉친다. 원인이 다르면 대응도 달라야 한다.
고치는 법
finish_reason == "length" 를 따로 기록한다. 한 줄이고, 처리 실패율 통계가 원인별로 갈린다.
폴백은 다르게
olmOCR 은 temperature 를 올려 재시도한다. 우리는 철학 6(같은 입력 → 같은 출력) 때문에 그럴 수 없다. 우리 사다리는 src/models.py 의 tier1 → tier2 모델 승격이다.
M7텍스트 verbatim 대조 — 가장 강한 단일 신호, 그러나 절반의 경로에만R1 G2

ExtractConf 에서 OCR 근거 신호만 쓴 구성(AUC 0.896)이 모델 내부 신호만 쓴 구성(0.880)을 이겼다. 핵심 특징은 하나다 — 추출된 값이 원본 OCR 텍스트에 문자 그대로 등장하는가. 여기에 유사도 임계 50 / 75 / 90% 를 더한다.

이것은 우리 ARCHITECTURE.md §4.4 가 이미 정한 역할 분담과 같은 말이다 — VLM 이 어느 값이 어느 필드인지 정하고, 텍스트 레이어가 그 글자를 보증한다.

적용 가능
xlsx·xlsm 118건 · PDF 텍스트 페이지(페이지 기준 68.3%) · 정비보고서 112건 중 111건이 텍스트 레이어 보유
적용 불가
tif 734건 (71.9%) — 텍스트 레이어가 아예 없다. 우리 주 경로다.
필요한 것
preprocess.probe_pages() 가 이미 페이지 텍스트를 잡아 온다. 대조 로직만 추가하면 된다.
주의
완전일치로 재면 OCR 잡음에 무너진다. 논문처럼 퍼지 대조 + 임계 3단으로 재야 한다.

tif 까지 넓히려면 로컬 OCR 엔진을 붙여야 하고, 그것은 이번 범위 밖이다. 다만 골든셋 30건에 대해서만 한 번 OCR 을 돌려 이 신호의 효과 상한을 재보는 것은 가능하고, 그 숫자가 후속 과제의 근거가 된다. 실험 E3.

M8텍스트 앵커링 — 시도할 값은 있으나 근거가 약하다R4 olmOCR

PDF 바이너리에서 텍스트 블록과 이미지의 좌표까지 함께 뽑아 프롬프트에 넣고, 렌더 이미지와 같이 준다. 형식은 이렇다.

RAW_TEXT_START

RAW_TEXT_ENDarXiv:2502.18443 Appendix A · 파인튜닝 시 상한 6,000자

이것을 채택하면 ARCHITECTURE.md §10 의 3-way A/B 중 "VLM+텍스트" 칸의 실제 구현이 된다. 지금 그 칸은 비어 있다.

근거 강도
약하다. 논문에 정량 ablation 이 없다. "환각이 뚜렷이 줄었다"는 정성 주장뿐이다.
범위 제한
저자 스스로 born-digital 전용임을 밝힌다 — 텍스트 레이어가 없는 스캔에서는 래스터 이미지에만 의존한다고 명시.
우리 판정
텍스트 레이어 있는 경로에서 직접 재본다. 논문 수치를 근거로 채택하지 않는다. 실험 E7.
충돌 없음
§4.4 와 모순되지 않는다 — 텍스트를 주더라도 어느 값이 어느 필드인지는 여전히 VLM 이 정한다.

Risk

마킹하면서 발견한 것 — 우리는 bbox 를 믿고 있다

M1 과 M4 둘 다 크롭을 전제한다. 그런데 크롭의 입력인 bbox 가 얼마나 정확한지를 우리는 재본 적이 없다. 벤치마크가 주는 답은 낙관적이지 않다.

대응 1 — 여백을 키운다

_crop() 의 우측·상하 여백 0.02 를 늘리고 최소 크롭 크기를 둔다. 크롭이 커지면 토큰이 늘지만, 페이지 전체보다는 훨씬 작다.

대응 2 — 불일치의 원인을 나눈다

재판독 결과에 raw_label 이 함께 오는지를 본다. 라벨이 보이면 값 불일치, 안 보이면 bbox 오류. 후자는 신뢰도를 깎지 않는다.

대응 3 — 우리 IoU 를 한 번 잰다

골든셋 30건의 bbox 를 눈으로 검수해 우리 코퍼스의 실제 IoU 를 기록한다. 공개 벤치와 다를 수 있고, 이 숫자가 있어야 여백값을 근거 있게 정한다. 실험 E8.
