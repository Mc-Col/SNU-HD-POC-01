# Insight Memory

핵심 판단과 그 근거를 보존하는 파일. 다시 도출하려면 비용이 큰 것, 또는 잊으면 같은 실수를 반복하게 되는 것만 기록함.
변경 이력은 `change_log.md` 참조.

## I. 문제 구조에 대한 인사이트

### 1. 이 문제의 실제 구조는 자기강화 악순환이다 ★★★
```
데이터 미활용 → 품질 요구 부재 → 거버넌스·표준 미수립
      ↑                                    ↓
현장 원본 재확인 100% ← 신뢰도 붕괴 ← 누락·오류 40%
```
개별 담당자의 성실성 문제가 아님. **소비자가 없는 데이터에는 품질 압력이 발생하지 않고, 품질이 낮으면 소비자가 더 줄어드는 구조**임.

**왜 중요한가** 이 인식이 없으면 "입력 자동화"로 문제를 정의하게 되고, 그러면 자동화 후에도 품질이 다시 저하됨. 목표는 입력 속도가 아니라 **소비 가능한 신뢰 수준의 확보**여야 함.

**도출 경로** 거버넌스 주체가 없는 이유를 물었을 때 "지금까지 이 데이터를 거의 활용하지 않았기 때문"이라는 답에서 인과가 확정됨. 이 한 문장이 40% 오류율의 원인을 설명함.

### 2. "왜 지금인가"의 답은 기술이 아니라 소비자다 ★★★
1순위는 **"디지털트윈 사전작업 착수로 처음으로 이 데이터의 소비자가 생겼다"**임. Vision AI 성숙은 3순위.

**왜 중요한가** "기술이 좋아져서 하자"는 강의 리뷰 체크리스트의 대표 오류(기술우선)로 읽히고, 사업 언어가 아님. **"소비자가 생겨서 하자"는 업무 언어이며 악순환 루프가 끊어지는 시점을 특정함.** 발표에서도 이 순서를 유지해야 함.

### 3. 손실은 유입분과 전량을 반드시 분리한다 ★★
| 구분 | 금액 | 성격 |
|---|---|---|
| 유입분 | 연 12.42억원 | **실제 집행 중인 비용** — 그런데 활용률 0%로 전액 미회수 |
| 전량 | 517.5억원 / 41.7년 | **집행조차 불가능한 미달성 규모** — 착수 가능성의 문제 |

**왜 중요한가** 합쳐서 "530억"으로 쓰면 과장으로 읽혀 신뢰를 잃음. 분리하면 각각 다른 결론으로 이어짐 — 전자는 "낭비 중", 후자는 "착수 불가". 후자가 이 과제의 최대 명분임.

### 4. 판단자와 1차 검토자가 동일인 → AI가 없던 검증 단계를 만든다 ★★
현행: 엔지니어가 입력하고 본인이 1차 승인 → **독립 검증 없음**. 실질 검증은 도면관리 담당자 1단계뿐.
AI 도입 후: AI가 1차 판단 → 엔지니어가 **실질적 독립 검토자로 전환** → 검증 단계가 하나 늘어남.

**왜 중요한가** "AI가 사람을 대체한다"가 아니라 "AI가 없던 검증을 만든다"는 프레임임. 이 과제의 부수 효과 중 가장 설득력이 높고, 사용자 수용성 리스크에 대한 답이기도 함.

## II. 기술·설계 판단

### 5. Fail Action의 ATO/ATC 역전이 규칙 계층의 존재 이유다 ★★★
```
Air-to-Open (ATO)  → 공기 상실 시 스프링이 닫음 → Fail CLOSE
Air-to-Close (ATC) → 공기 상실 시 스프링이 엶   → Fail OPEN
```
문자열만 보고 "Air to Open → Fail Open"으로 뽑으면 **정반대**이고, 이건 안전 필드임.

**왜 중요한가**
- 규칙 기반 계층이 "보완 기능"이 아니라 **안전 요건**임을 증명하는 사례
- 오적재 0건을 모델 성능만으로 보장할 수 없다는 논거
- 앵커링 완화 설계(근거 원문 + 변환 과정 병기)의 필요성 근거
- 도메인 규칙이 개인 암묵지로만 존재한다는 문제의 구체적 증거

### 6. "채우되 리뷰필요 표시"가 빈칸보다 우수하다 ★★★
초기 AI 설계는 "불확실하면 공백 반환"이었으나 **사용자 교정이 더 우수함**. 이유: 제안값이 있으면 사람에게 **검증 기준점**이 생겨 확인이 훨씬 빠름. 빈칸은 결국 백지 입력이라 건당 1.45시간 문제로 되돌아감.

단, 상태를 **3개로 분리**해야 함. AI가 값을 못 내는 이유가 두 종류이기 때문:

| 상황 | 처리 | 이유 |
|---|---|---|
| 확신도 낮음 (흐린 스캔 등) | 값 제시 + `리뷰필요` | 검증 기준점 제공 |
| 문서에 근거 없음 (레거시 등) | `N/A` + 비고에 판정 근거 | **"채우기"를 강제하면 환각을 강제하는 것** |

**원칙 정합성** "모르면 빈칸"과 "채우되 표시"는 적용 층위가 다름 — 스테이징(AI 출력)은 제안값 허용, 확정 레코드는 추정값 금지. 모순 아님. 워크북에 이걸 명시해야 자기모순으로 읽히지 않음.

**비고 칼럼의 역할** 같은 `N/A`라도 확신 수준이 다름(카탈로그로 미지원 확인됨 vs 모델명 미판독으로 확인 불가). **비고가 그 차이를 승인자에게 전달**하여, 레코드는 완결되고 의심은 보존됨. 별도 보류 상태를 만들 필요가 없어짐.

### 7. 오적재를 리뷰필요로 전환하는 것이 곧 안전 확보다 ★★★
오적재는 **자동확정으로 통과했는데 틀린 것만** 해당함. 리뷰필요로 표시된 건 사람이 보므로 오적재가 아님.

따라서 안전과 효율의 트레이드오프가 **확신도 임계값 하나로 정리됨**:
- 임계값을 높이면 → 오적재↓, 리뷰필요↑ (안전하지만 사람 부담 증가)
- 임계값을 낮추면 → 오적재↑, 리뷰필요↓ (효율적이지만 위험)

**왜 중요한가** 이것이 후속 Contextual Bandit의 대상임. 보상 = −(오적재비용 × 안전가중) − (검토시간 × 50,000원/h). 그리고 KPI를 정확도 하나가 아닌 위험/효익/비용 3축으로 나눠야 하는 이유임.

### 8. 100% 정확도는 100건 표본으로 입증할 수 없다 ★★
100건에서 오류 0건이어도 실제 오류율의 95% 신뢰상한은 **약 3%** (rule of three, 3/n).

**조치** "정확도 100%" 대신 **"오적재 0건 관측 + 확신도 미달 시 100% 강제 에스컬레이션"**으로 표현. 즉 **모델 정확도가 아니라 시스템 설계로 100%를 보장**함. 목표는 그대로 유지되면서 증명 가능해짐.

### 9. 엑셀은 셀 좌표가 아니라 헤더 텍스트로 매핑한다 ★★
벤더 양식이 "포맷은 유지되되 디테일이 바뀜"(옵션 추가, 엑셀 포맷 변경)이므로 `B7` 같은 좌표 기준은 깨짐. **`'Body Size' 라벨 우측 셀`** 방식이면 행·열 이동에 무관.

**부가 효과** 이 헤더 파서가 그대로 **베이스라인 ②(규칙 단독)로 재사용**되어 추가 비용 없이 H5(VLM 필요성) 검증이 가능해짐.

### 10. VLM 선택의 진짜 근거는 "디테일이 바뀐다"는 조건이다 ★★
벤더당 최대 3종 × 5개사 = **양식 변종 최대 15종**에 레거시 혼재. 여기에 "없던 옵션 추가 / 엑셀 포맷 변경 / 오래된 데이터시트" 형태로 변동.

이 조건이 정확히 **전통 ML과 템플릿 파싱이 실패하고 문서 이해가 성공하는 영역**임 — 전자는 변종별 학습 데이터(변종당 수백~수천 건)가 필요한데 확보 가능량이 100건 수준.

**왜 중요한가** VLM을 "최신 기술이라서"가 아니라 **현업 조건에서 도출된 결론**으로 쓸 수 있게 됨. Part F의 비교가 사후 정당화가 아니게 되는 핵심 근거.

### 11. 주 접근법은 단일 기술이 아니라 조합이다 ★★
`VLM 정보추출` **+** `규칙 기반 검증` — 어느 한쪽만으로는 요건을 충족하지 못함.
- VLM 없이: 양식 변종 대응 불가
- 규칙 없이: 오적재 0건 보장 불가

**왜 중요한가** 강의 Part F 원칙이 "하나의 최신 기술보다 현장 조건에 맞는 조합을 고른다"임. 단일 기술을 답으로 쓰면 감점 구간.

### 12. 생성형 AI에 값 결정 권한을 주지 않는다 ★★
정규화·요약에는 사용하되 **값 결정은 허용값 리스트 내 선택으로 한정**하고 단위 변환은 결정론적 계산으로 처리함.

**근거** 환각이 기준정보에 유입되면 이 과제가 해결하려는 문제(부정확한 기준정보)를 정확히 재생산함. 회사 원칙(모르면 채우지 않음)과도 일치.

### 13. 강화학습의 진짜 자리는 로드맵 종착점이다 ★★
과제 A는 단일 단계 지도학습 문제 — 행동이 후속 상태를 변화시키지 않고 정답이 직접 주어짐. RL을 억지로 넣으면 "기술우선" 오류.

```
A. 데이터시트 → 기준정보 추출      (VLM + 규칙)
B. 정비이력 자동정비                (동일 파이프라인, 문서타입 확장)
C. 자산등급 산정                    (B 산출물 기반 스코어링)
D. 정비정책·예지보전 스케줄 최적화   ← RL이 진짜 맞는 곳
                                     순차적 · 상태변화 · 비용/보상 명확
```
**"검토했고 어디에 쓸지 알지만 지금은 조건 미충족"**이 억지 삽입보다 강한 포지션임. 정당한 중간 접점은 HITL 임계값 최적화(Contextual Bandit).

### 14. PoC 아키텍처는 에이전트화를 전제로 설계한다 ★★
PoC는 결정론적 순차 파이프라인이지만, **각 단계를 독립 호출 가능한 도구 단위로 분리**하고 상태·로그를 외부화함.

**근거** 후속 과제 B(정비이력)의 원천이 PM 워크오더 자유텍스트·체크리스트 체크박스·수기 일지·팀별 엑셀 4종으로 확대되면 경로 선택이 실질적 판단 문제가 되어 결정론적 분기로는 대응 불가함. 그때 재구현하면 손해.

## III. 검증 설계

### 15. 골든셋 100건을 두 번 쓴다 ★★★
정답 라벨을 만들 때 동일 100 Tag의 마스터DB 등록값을 대조하면 **추가 3시간으로 현행 오류율 실측치가 나옴**.

| 효과 | 내용 |
|---|---|
| ① | Part H 기준선이 "체감 40%"에서 **실측치로 승격** |
| ② | 필드별 오류율 분포 → 취약 필드 특정 |
| ③ | 40% 체감치의 과대/과소 검증 |
| ④ | **파이프라인 성공과 무관하게 확보되는 결과** — 일정 헤지 |

예상 부수효과: 스마트 계장 필드(Communication Protocol, Diagnostic Tier)의 누락률이 압도적으로 높게 나올 것 — 스키마에 자리가 없었으므로. 그러면 "기술 변화 미반영" 문제도 수치로 입증됨.

### 16. 베이스라인 ②(규칙 단독)가 Part F의 논리를 실증한다 ★★
VLM을 제외한 규칙 단독 파이프라인과 비교하지 않으면, **"VLM이 실제로 필요했는가"에 답할 수 없고 Part F의 비교가 사후 정당화로 남음**.

라벨링용 헤더 파서를 재사용하므로 추가 비용이 거의 0. 가성비가 가장 좋은 검증 항목.

### 17. 레거시가 전량의 대부분이므로 연식 축이 필수다 ★★
```
유입분 (월 600건)  → 대체로 현행 양식
전량  (30만 태그)  → 대체로 레거시 양식
```
현행 양식으로만 검증하면 **과제의 최대 명분(517억·41.7년)과 검증 대상이 어긋남**. 골든 100건을 현행 70 / 레거시 30으로 층화하고 별도 집계해야 함.

레거시 성능이 현행 대비 20%p 이상 낮으면 Stop이 아니라 **조건부 축소**(유입분 한정 적용 + 레거시 대응 별도 과제 분리)로 처리.

### 18. 목표값 / 최소 허용선 / 중단선을 3단으로 분리한다 ★★
정확도 목표 98% / Go 기준 95% / Stop 기준 90% 미만.

**왜 중요한가** 목표 하나만 쓰면 미달 시 전부 실패로 읽힘. 3단으로 나누면 판정이 실제 의사결정처럼 작동하고, "목표는 못 채웠지만 진행 근거는 있다"는 결론이 가능해짐.

### 19. 98%는 임의값이며, 근거는 "재확인을 멈추는 임계"에서 온다 ★
사용자가 임의로 부여한 값임. 최선의 보정 경로는 **신뢰 임계 조사** — 오류율 40%에서 재확인 100%가 발생했으므로 재확인을 멈추게 하는 품질 임계가 존재함. 사용자 수용성 조사에서 "정확도 몇 %면 원본을 다시 안 볼 것인가"를 물어 근거를 확보.

이러면 **"98%가 목표인 이유는 그 수준에서 현장이 재확인을 멈추기 때문"**이 되어 임의값이 업무 근거를 갖고, Part A-2의 재확인 100% 문제와 직접 연결됨.

### 20. 홀드아웃은 1회만 개봉한다 ★
골든 100건을 개발 30 / 홀드아웃 70으로 분리. VLM은 학습이 없지만 **프롬프트 엔지니어링이 과적합을 유발**하므로, 100건 전부로 튜닝하면 KPI가 무의미해짐. 홀드아웃 결과를 보고 튜닝하면 측정 무효.

### 21. 1,000건과 100건의 용도가 다르다 ★
- **1,000건** 처리 안정성(지연·처리량·실패율)만 검증. 사람이 정확도 검증 안 함
- **100건** 정확도 검증 전용

이 구분이 없으면 1,000건 전수 검증이라는 불가능한 계획이 됨.

## IV. 프로젝트 운영

### 22. 산출물을 A/B로 분리해 일정 리스크를 헤지한다 ★★
| 구분 | 산출물 | 확보 시점 |
|---|---|---|
| **A. 파이프라인 무관** | 스키마 정의서 / 정규화 규칙표 / 정답셋 100건 / 현행 오류율 실측치 | **8/24** |
| B. 성능 의존 | 파이프라인 / 데모 웹 / KPI / Go·Stop 판정 | 8/26 |

**왜 중요한가** 8/27 발표에 8/26 오후 하루만 남으므로, 파이프라인이 8/25에 안 되면 발표가 무너짐. A가 8/24에 확보되면 **최악의 경우에도 발표는 성립**함. 발표 자료 골격을 8/24에 만들고 KPI만 나중에 채우는 방식.

### 23. PoC가 중단되어도 남는 자산이 있다 ★★
스키마 정의서·정규화 규칙표·정답셋·오류율 실측치는 **어떤 접근법을 택하든 필요한 전제**이므로 투자 손실이 발생하지 않음.

**왜 중요한가** PoC 제안의 리스크를 크게 낮추는 논거. Part E-3, J(예상 산출물), H-1(Go 기준 ⑥)에서 반복 사용 중.

### 24. 최상위 리스크는 기술이 아니라 거버넌스 부재다 ★★
PoC가 성공해도 **결과를 반영할 승인 경로가 없음**. 스키마 정의서를 누가 확정하는지도 불명확.

**조치** PoC는 잠정안으로 진행하고, 디지털트윈 사전작업과 연계하여 거버넌스 주체 지정을 제안함. 책임 소재는 최종 승인자(도면관리 담당자)에 유지되며 AI는 제안만 수행한다는 원칙을 문서화.

### 25. 워크북 내용은 소스이고 docx는 빌드 산출물이다 ★★
`tools/content_*.py` (소스) → `tools/build.py` → docx + md (산출물).

**왜 중요한가**
- rev.B가 명령 한 줄 (`python tools/build.py rev.B`)
- 재빌드 결과가 바이트 동일함을 확인함 (재현성)
- md 산출물로 diff·리뷰 가능
- Readme 요구사항 "지속 실행·검증·개선 루프 구조" 충족

**주의** md는 자동 생성물이므로 직접 편집하지 말 것. docx가 Word에서 열려 있으면 빌드가 잠금으로 실패함(명시적 중단 메시지 출력됨).

## V. 프롬프팅·협업 방식

### 26. 아는 숫자를 먼저 외부화한다 ★★
초기 Readme와 첫 대화 모두 정량 근거가 비어 있었으나, 물으면 즉답 가능한 상태였음. **정보 부족이 아니라 외부화 습관의 문제**임 — 기획자 업무 패턴(문제정의를 먼저 상세히, 수치는 마지막에)에서 기인함.

**왜 중요한가** 기획서 독자는 빈칸을 "미정"으로 읽지만 **LLM은 빈칸을 환각으로 채움**. 순서를 바꿀 필요는 없고, "내가 아는 대략치"를 처음에 던져두는 것만으로 해결됨.

### 27. 프롬프트는 결론을 전달하는 것이 아니라 좋은 추론의 조건을 만드는 것이다 ★★
초기 Readme(Gemini 작성)는 기술·폴더구조·범위를 모두 확정한 **명세**였고, 그래서 기술우선·범위과대 문제가 프롬프트 레벨에서 이미 박혀 있었음. 반면 대화에서는 문제를 열어두고 검토를 요청했고 결과가 훨씬 나았음.

같은 사람·같은 도메인 지식인데 결과가 갈린 원인. 제출 회고에 쓸 내용.

### 28. 도메인 전문가의 교정이 모델 제안보다 정확했던 사례 ★★
- `분류체계 재정의` → `기준정보 체계 재정의` (용어)
- 과제 C(자산등급) 앞에 **B(정비이력 자동정비) 신설** — 정비이력이 비정형이면 등급 알고리즘의 입력이 없다는 인과
- "채우되 리뷰필요 표시" — AI의 빈칸 설계보다 우수
- "N/A + 비고 칼럼" — AI가 제시한 A/B 선택지보다 깔끔

**왜 중요한가** AX 과제의 핵심 메시지 그 자체임. 발표·회고에서 전면에 낼 소재.

### 29. 착수 전 검토 요청이 가장 값이 컸다 ★★
"본격작업 하기 전에 의견을 먼저 간단하게 줘" 한 줄로 기술선점·범위과대·정량근거 부재 3건을 사전 검출함. 이것 없이 바로 작성했다면 세 문제를 품은 문서가 나왔을 것.
